# ADR-006: i18next for internationalisation

**Date:** 2026-01-18
**Status:** Accepted
**Deciders:** mITyGarden core team

## Context

mITyGarden targets at minimum three locales from day one: English (`en`), Dutch (`nl`), and French (`fr`). All user-visible strings must be translatable. The i18n system must:

- Work in React components (hooks) and outside React (store action messages, export text).
- Support lazy loading of translation namespaces.
- Allow locale switching at runtime without a full page reload.
- Be installable as a shared package (`@mity-garden/i18n`) consumed by all apps.

## Decision

Use **i18next** with `react-i18next` for React integration.

The shared `packages/i18n` package exposes:
- `createI18n(config?)` — initialises the i18next instance with JSON translation files.
- `setSharedI18n(instance)` / `getSharedI18n()` — singleton accessor used outside React.
- Translation files in `packages/i18n/src/locales/{locale}/common.json`.

Locale switching is handled by `uiStore.setLocale()`, which calls `i18n.changeLanguage()`.

## Alternatives considered

| Alternative | Reason rejected |
|-------------|----------------|
| react-intl (FormatJS) | More complex ICU message format; React-only (no clean non-React usage) |
| Lingui | Excellent performance; compile step adds CI complexity |
| Custom Map / JSON lookup | No plural handling, no interpolation, no lazy loading; would need to reinvent the wheel |
| next-intl | Next.js-specific; not applicable to a Vite SPA |

## Consequences

**Positive:**
- Mature ecosystem; plugins for plural rules, date formatting, namespacing.
- `useTranslation("common")` hook is ergonomic in components.
- `getSharedI18n().t("key")` works outside React for export text generation.
- Adding a locale requires only a new JSON file and one type update.

**Negative / trade-offs:**
- All translation JSON is bundled at build time (no lazy namespace loading in current setup). Will matter at scale if the key count grows significantly.
- i18next's plugin architecture means extra packages (`i18next-resources-to-backend`, etc.) are needed for advanced loading patterns.
